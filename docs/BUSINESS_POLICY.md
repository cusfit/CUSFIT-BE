## 읽는 법

- 항목 ID는 도메인 약자와 번호입니다. `C`(공통), `U`(user), `T`(terms), `CA`(catalog), `R`(recipe), `RP`(report), `N`(notification), `S`(support).
- 스키마 영향이 있는 항목은 엔티티와 Flyway 작업 전에 정해야 합니다. 맨 아래 "결정 순서"에 정리했습니다.
- 법령이 걸린 항목은 "법무 확인 필요"로 표시했습니다. 이 문서의 추천은 법률 검토를 대신하지 않습니다.

## 1. 공통

C-01, C-02를 테이블 단위로 옮긴 구현 결정(삭제 방식, FK, 카운터 처리 등)은 `docs/TECH_DECISIONS.md`에 있습니다.

### C-01. 삭제 방식 (soft delete와 hard delete)

- 결정할 것: 사용자가 지운 데이터를 바로 물리 삭제할지, `deleted_at`으로 표시만 하고 나중에 지울지.
- 선택지
  - A. 전부 hard delete. 단순하지만 신고 처리나 분쟁 확인에 쓸 기록이 남지 않습니다.
  - B. 콘텐츠(레시피)만 soft delete하고 일정 기간 뒤 hard delete. 반응(좋아요, 저장)이나 알림 같은 부속 데이터는 hard delete.
  - C. 전부 soft delete. 모든 조회에 `deleted_at IS NULL` 조건이 붙어 실수하기 쉽습니다.
- 추천: B. 레시피는 신고가 걸려 있을 수 있으니 soft delete 후 30일 뒤 배치로 hard delete합니다. 좋아요·저장·알림은 바로 지웁니다.
- 영향: `recipe.deleted_at` 컬럼, 정리 배치, 리포지토리 조회 조건.

### C-02. 탈퇴한 사용자 행(row)의 처리

- 결정할 것: 탈퇴한 사용자가 남긴 레시피(U-05)가 있을 때 `users` 행을 지울지, 개인정보만 지운 껍데기로 남길지.
- 선택지
  - A. `users` 행을 지우고 레시피의 `author_id`를 NULL로 바꿈. 레시피를 다루는 모든 코드가 작성자 NULL을 처리해야 합니다.
  - B. `users` 행은 남기고 상태를 `WITHDRAWN`으로 바꾸고 이메일·닉네임 등 개인정보 컬럼을 비움. 소셜 계정 연결 행은 삭제.
- 추천: B. 도메인 간 참조를 ID로만 하기로 했으므로(컨벤션 7장) ID가 계속 유효한 편이 단순합니다. 화면에는 작성자를 "탈퇴한 사용자"로 표시합니다.
- 영향: `users.status`, 개인정보 컬럼 NULL 허용, 닉네임 유니크 제약을 "NULL이 아닌 값만" 대상으로.

### C-03. 운영자 기능

- 결정할 것: 신고 처리, 공지·FAQ 작성, 문의 답변, 브랜드·메뉴 관리를 누가 어떻게 하는지. Figma에는 운영자 화면이 없습니다.
- 선택지
  - A. 관리자 API를 만들고 운영자는 Swagger나 간단한 도구로 호출.
  - B. 운영자가 DB에 직접 SQL을 실행.
- 추천: A. JWT 권한(`ROLE_ADMIN`)으로 막은 최소한의 관리자 API를 둡니다. 직접 SQL은 실수 위험이 크고 기록이 남지 않습니다. 권한 클레임 구조는 아직 TBD인 인증 흐름(CLAUDE.md)과 같이 정해야 합니다.
- 영향: 각 도메인에 관리자용 서비스 메서드, 보안 설정.

### C-04. 알림·화면 문구에 다른 사용자 닉네임을 넣을지

- 결정할 것: "OO님이 회원님의 레시피를 저장했어요"처럼 행위자를 드러낼지.
- 추천: 넣지 않습니다. Figma 알림 예시("회원님의 레시피가 100번 저장됐어요")도 행위자가 없습니다. 행위자를 넣지 않으면 탈퇴나 닉네임 변경 때 이미 보낸 알림을 고칠 필요가 없습니다.

## 2. user (회원)

### U-01. 로그인 수단과 계정 연결

- 근거: Figma 로그인 화면은 Apple, 구글 두 가지입니다.
- 결정할 것: 같은 이메일로 Apple과 구글에 각각 가입하면 한 계정으로 합칠지.
- 추천: 합치지 않고 별개 계정으로 둡니다. Apple은 "나의 이메일 가리기"를 고르면 릴레이 주소를 주기 때문에 이메일로 같은 사람인지 판단할 수 없습니다. 식별은 `(provider, provider_user_id)`로만 합니다.
- 영향: `social_account`에 `(provider, provider_user_id)` 유니크 제약. 이메일에는 유니크 제약을 걸지 않습니다.

### U-02. 닉네임 규칙

- 근거: 회원가입 화면 "2~12자", "한글, 영문, 숫자를 사용할 수 있어요", 디자인페이지 "공백없이 2자 이상 12자 이하", 중복 시 "이미 사용 중인 닉네임이에요"와 대체 닉네임 제안.
- 결정할 것
  - 영문 대소문자를 구분해서 중복을 판단할지
  - 금칙어(운영자, 관리자, cusfit, 욕설 등)를 막을지
  - 닉네임 변경 횟수나 주기를 제한할지
  - 탈퇴한 사용자의 닉네임을 바로 다시 쓸 수 있게 할지
- 추천
  - 대소문자를 구분하지 않고 중복을 판단합니다. `Ondo`와 `ondo`가 둘 다 있으면 사칭에 쓰일 수 있습니다.
  - 운영 사칭 단어만 막는 짧은 금칙어 목록으로 시작합니다. 욕설 필터는 신고(RP)로 대응합니다.
  - 변경 제한은 두지 않습니다. 알림에 닉네임을 넣지 않으므로(C-04) 변경 비용이 작습니다.
  - 탈퇴하면 닉네임을 비우므로(C-02) 바로 다시 쓸 수 있습니다.
- 영향: 정규화한 닉네임 컬럼(소문자) 또는 함수 기반 유니크 인덱스.

### U-03. 나이 확인

- 근거: 회원가입 "만 14세 이상입니다 (필수)" 체크.
- 추천: 본인 체크만 받고 체크 시각을 약관 동의 이력과 같이 저장합니다. 만 14세 미만은 법정대리인 동의가 필요하므로 가입을 받지 않습니다. (법무 확인 필요)

### U-04. 탈퇴 유예 기간

- 근거: 탈퇴 화면 "삭제된 정보는 다시 복구할 수 없어요", 최종 확인 팝업 "탈퇴한 계정과 정보는 복구할 수 없습니다", 개인정보처리방침 "회원 탈퇴 시 개인정보를 지체 없이 파기합니다".
- 선택지
  - A. 즉시 탈퇴. 확인 후 바로 처리.
  - B. 유예 기간(예: 14일) 동안 복구 가능.
- 추천: A. 화면 문구와 개인정보처리방침이 모두 즉시 삭제를 약속합니다. 유예 기간을 두려면 이 문구들부터 바꿔야 합니다.

### U-05. 탈퇴한 사용자가 만든 레시피 (핵심)

- 근거: 와이어프레임·디자인 탈퇴 화면에 "(선택) 내 레시피도 함께 삭제할까요? 삭제하면 다른 커스핏 사용자들이 레시피를 확인할 수 없어요" 체크박스가 있습니다. 화면정의서는 레시피를 무조건 지우는 이전 문구입니다(0-2).
- 결정할 것: 체크하지 않은 경우 레시피를 남길지, 남기면 어떻게 보일지.
- 추천
  - 체크하면 레시피를 삭제(C-01 soft delete)합니다. 체크하지 않으면 레시피를 남기고 작성자를 "탈퇴한 사용자"로 표시합니다.
  - 남긴 레시피는 소유자가 사라지므로 나중에 수정하거나 지울 수 없습니다. 탈퇴 화면에 "남긴 레시피는 탈퇴 후 직접 삭제할 수 없어요" 문구 추가를 디자인에 요청합니다.
  - 남긴 레시피도 신고와 블라인드(RP) 대상입니다.
  - 탐색의 "작성자 검색"에서는 탈퇴한 사용자를 검색할 수 없습니다.
- 대안: 체크박스 기본값을 "삭제"로 둘지 "남김"으로 둘지도 정해야 합니다. 개인정보 쪽으로 안전한 기본값은 "삭제"이고, 콘텐츠를 지키는 기본값은 "남김"입니다. 추천은 체크 해제(남김)가 기본인 현재 디자인 그대로입니다.

### U-06. 탈퇴 시 다른 데이터의 처리

탈퇴 한 번에 여러 도메인이 같이 움직입니다. 아래 표가 추천안입니다.

| 데이터 | 도메인 | 처리 | 이유 |
|---|---|---|---|
| 이메일, 닉네임, 프로필 | user | 즉시 비움 (C-02) | 개인정보처리방침 "지체 없이 파기" |
| 소셜 계정 연결 | user | 즉시 삭제, Apple은 토큰 철회 API 호출 | 같은 소셜 계정으로 다시 가입하면 새 회원으로 처리. Apple은 탈퇴 시 토큰 철회를 요구합니다 (확인 필요: 인증 구조가 정해지면 위치 결정) |
| 내가 만든 레시피 | recipe | U-05 선택에 따름 | |
| 내가 누른 좋아요, 내가 한 저장 | recipe | 즉시 삭제, 상대 레시피의 카운트 감소 | 탈퇴 화면 "좋아요 및 활동 기록" 삭제 |
| 남이 내 레시피에 한 좋아요, 저장 | recipe | 레시피를 남기면 유지, 지우면 같이 삭제 | R-07 |
| AI 피드백 | recipe | 작성자 연결만 끊고 보관 | 개인정보가 아닌 품질 데이터. 단, "기타" 자유 입력에 개인정보가 들어갈 수 있어 확인 필요 |
| 약관 동의 이력 | terms | 즉시 삭제 | 법령상 보관 근거를 찾지 못하면 삭제 (법무 확인 필요) |
| 내가 한 신고 | report | 신고자 연결만 끊고 보관 | 처리 이력과 통계 |
| 내 레시피에 대한 신고 | report | 레시피를 남기면 계속 처리, 지우면 "대상 삭제"로 종료 | |
| 받은 알림 | notification | 즉시 삭제 | |
| 알림 설정, FCM 토큰 | notification | 즉시 삭제 | 탈퇴 후 푸시가 가면 안 됩니다 |
| 1:1 문의와 첨부 이미지 | support | 즉시 삭제 (S3 이미지 포함) | 답변 이메일이 개인정보입니다 |
| 탈퇴 사유 | user | 사용자와 연결하지 않은 채로 보관 | 화면정의서 "탈퇴 사유 (선택)" |

- 처리 방식: user 서비스가 탈퇴를 처리하고 `UserWithdrawnEvent`를 발행합니다. 다른 도메인은 이 이벤트를 받아 자기 데이터를 정리합니다(컨벤션 7장). DB 정리는 같은 트랜잭션에서 하고, S3 삭제와 Apple 토큰 철회처럼 외부 호출은 `@TransactionalEventListener(AFTER_COMMIT)`에서 합니다.

### U-07. 재가입 제한

- 결정할 것: 탈퇴 후 같은 소셜 계정으로 바로 다시 가입할 수 있게 할지.
- 추천: MVP에서는 제한하지 않습니다. 제재 기능(RP-06)을 도입하면 제재 회피를 막기 위해 제재받은 계정의 소셜 ID 해시만 일정 기간 보관하는 방식을 다시 검토합니다. 이 경우 개인정보처리방침에 보관 항목을 적어야 합니다.

### U-08. 프로필 이미지

- 근거: Figma 프로필 수정 화면에는 닉네임만 있습니다.
- 추천: MVP에서는 프로필 이미지를 두지 않습니다. 업로드, 삭제, 탈퇴 시 S3 정리를 모두 생략할 수 있습니다.

- 추천: 브랜드, 기본 메뉴, 레시피 이름, 옵션 1개 이상을 필수로 합니다. 레시피 이름은 카드 제목이라 200자 대신 30자를 제안합니다(디자인 확인 필요).

- 추천: 사용자당 AI 분석은 하루 20회, 레시피 생성은 하루 30개로 시작합니다. 숫자는 출시 후 지표를 보고 조정합니다. 초과하면 `INVALID_REQUEST`가 아니라 클라이언트가 분기할 수 있도록 별도 `ErrorCode`를 둡니다(컨벤션 2.3).

### R-04. 중복 레시피 판정

- 근거: 중복 레시피 경고 "같은 기본 메뉴와 커스텀 옵션으로 등록된 레시피가 있어요", 버튼 "기존 레시피 보기 / 옵션 수정하기". 화면정의서에서 이 항목은 `검토 필요` 상태이고, 설명은 "기존 본인 레시피 상세로 이동한다"인데 팝업 예시에는 "온도님의 레시피"가 보입니다.
- 결정할 것: 중복 범위를 내 레시피로 한정할지, 전체 사용자로 넓힐지.
- 선택지
  - A. 본인 레시피끼리만 막음. 다른 사람과 같은 조합은 저장 가능.
  - B. 전체 사용자 기준으로 막음. 나중에 가입한 사람은 같은 조합을 자기 기록으로 남길 수 없습니다.
  - C. 본인 중복은 막고, 타인 중복은 안내만 하고 저장 허용.
- 추천: A로 시작합니다. 기록 서비스라서 남과 같은 조합도 내 목록에 남길 수 있어야 합니다. 같은 레시피가 탐색에 여러 개 보이는 문제가 커지면 C로 바꿉니다.
- 판정 기준: 기본 메뉴 ID가 같고, 그룹별 옵션 집합이 같으면 중복입니다. 순서와 앞뒤 공백, 대소문자는 무시합니다. 직접 입력 옵션은 글자가 조금만 달라도 다른 옵션으로 봅니다.
- 영향: 옵션을 정규화한 시그니처(해시) 컬럼과 `(author_id, signature)` 유니크 인덱스. 이 결정은 스키마에 들어가므로 recipe 엔티티 작업 전에 정해야 합니다.

- 추천: A. 단순하고, 작성자가 오타를 고치면 모두에게 반영되는 편이 자연스럽습니다. 수정 후에도 중복 판정(R-04)을 다시 실행합니다.

### R-06. 본인 레시피에 좋아요·저장

- 근거: "레시피 자세히 보기 - 본인" 화면에는 좋아요·저장 버튼이 없고, "타인" 화면에만 있습니다.

### R-07. 레시피 삭제 시 좋아요·저장

- 추천: A. 레시피는 soft delete(C-01), 좋아요·저장 행은 같은 트랜잭션에서 hard delete합니다. B와 C는 Figma에 화면이 없습니다.

- 추천: 인기 = 저장 수, 같으면 최신순. MVP에서는 전체 기간 누적으로 하고, 오래된 레시피가 상위를 독점하면 최근 N일 가중치를 검토합니다. 카드 숫자도 저장 수로 맞춥니다(디자인 확인 필요).
- 영향: `recipe.save_count` 인덱스. 좋아요·저장 카운트 동시성은 이미 정한 원자적 UPDATE 방식을 씁니다.

### RP-05. 작성자 통지와 이의 제기

- 근거: 이용약관 제4조 "서비스 운영 정책에 위배되는 콘텐츠는 안내 후 제한되거나 삭제될 수 있습니다".
- 추천: 블라인드와 삭제 확정 때 작성자에게 서비스 알림을 보냅니다. 약관에 "안내 후"라고 썼으므로 통지는 필요합니다. 이의 제기는 별도 화면 없이 1:1 문의로 받습니다.

### RP-06. 사용자 제재

- 결정할 것: 블라인드가 반복되는 사용자를 정지할지.
- 추천: MVP에서는 자동 정지를 두지 않고 운영자가 수동으로 판단합니다. 정지 기능이 생기면 U-07(재가입 제한)도 함께 정합니다.

## 7. notification (알림)

### N-01. 알림 종류

- 근거: 알림 화면 탭(전체, 활동, 소식), 알림 설정 4개(전체 알림, 레시피 활동, 브랜드·레시피 소식, 서비스 알림).

| 종류 | 탭 | 설정 항목 | 예시 |
|---|---|---|---|
| 내 레시피 좋아요·저장 | 활동 | 레시피 활동 | "회원님의 레시피가 100번 저장됐어요" |
| 인기 레시피 | 소식 | 브랜드·레시피 소식 | "이번주 인기 레시피 Top 10" |
| 공지·업데이트 | 소식 | 서비스 알림 | "cusfit 서비스 업데이트 안내" |
| 블라인드·삭제 통지 (RP-05) | 활동 | 끌 수 없음 | Figma에 없음, 추가 필요 |

### N-02. 좋아요·저장 알림 빈도

- 결정할 것: 좋아요·저장이 생길 때마다 알릴지, 묶어서 알릴지.
- 추천: 누적 기준(1, 10, 50, 100, 이후 100 단위)에 도달할 때만 알립니다. Figma 예시도 "100번 저장됐어요"입니다. 취소했다가 다시 눌러 같은 기준을 넘으면 다시 보내지 않도록 레시피별로 마지막 알림 기준을 저장합니다.
- 영향: 기준 기록 컬럼 또는 테이블.

### N-03. "저장한 브랜드"의 뜻

- 근거: 알림 설정 "저장한 브랜드의 인기 레시피 소식", 알림 권한 팝업 "저장한 브랜드의 인기 레시피". 그런데 브랜드를 저장하는 기능은 IA에 없습니다.
- 선택지
  - A. 내가 저장한 레시피들의 브랜드로 해석.
  - B. 브랜드 즐겨찾기 기능을 새로 만듦.
  - C. 문구를 "인기 레시피 소식"으로 바꾸고 브랜드 조건을 뺌.
- 추천: C. 사용자 수가 적은 초기에는 브랜드별로 나눠 보낼 만큼 콘텐츠가 없습니다. A는 문구와 동작이 어긋나고, B는 새 기능입니다.

### N-04. 보관 기간과 대상 삭제

- 추천
  - 알림은 90일 뒤 삭제합니다.
  - 알림을 눌렀는데 대상 레시피가 삭제·블라인드되었으면 R-09의 안내 화면으로 보냅니다.
  - 내 행동으로 생긴 알림은 보내지 않습니다(R-06으로 이미 막힘).

### N-05. 기기 토큰

- 근거: 플랜의 notification 도메인 엔티티(Notification, NotificationSetting)에 FCM 토큰 저장소가 없습니다.
- 추천: notification 도메인에 `DeviceToken(user_id, token, platform, updated_at)`을 추가합니다. 로그아웃하면 그 기기 토큰만, 탈퇴하면 전부 지웁니다. FCM이 무효 토큰을 알려 주면 바로 지웁니다.
- 영향: 엔티티 1개 추가. 도메인 작업 범위가 바뀌므로 플랜에도 반영해야 합니다.

### N-06. 발송 시간

- 추천: 소식성 알림은 21시~8시에 보내지 않습니다(T-02와 함께 법무 확인 필요). 활동 알림은 시간 제한 없이 보냅니다.

## 8. support (공지, FAQ, 1:1 문의)

### S-01. 공지

- 근거: 공지 목록의 "중요" 배지, 등록일 순 정렬.
- 추천: "중요" 공지는 목록 맨 위에 고정합니다. 공지 등록 시 서비스 알림(N-01) 발송 여부를 운영자가 고릅니다.

### S-02. 1:1 문의

- 근거: 문의 유형 선택, 내용 500자, 이미지 첨부(선택), "가입한 이메일로 답변을 보내드려요".
- 결정할 것: 문의 유형 목록, 이미지 개수와 용량, 앱 안에서 답변을 보여 줄지.
- 추천
  - 유형: 서비스 이용, 오류 신고, 계정, 레시피·AI, 메뉴 추가 요청(CA-02), 신고 이의 제기(RP-05), 기타.
  - 이미지는 최대 3장, 장당 10MB, jpg·png·heic.
  - 답변은 이메일로만 보내고 앱 안 문의 내역 화면은 만들지 않습니다(Figma에 없음). DB에는 답변 내용과 답변 시각을 남깁니다.
- 주의: Apple 로그인 사용자가 이메일 가리기를 고르면 릴레이 주소로 답변해야 합니다. 이 주소로 메일을 보내려면 Apple Developer에 발신 도메인을 등록해야 합니다. 등록하지 않으면 답변이 전달되지 않습니다.

### S-03. FAQ

- 추천: 운영자가 관리자 API로 관리합니다. 고객센터 화면에 FAQ 검색이 있으므로 제목·본문 단순 LIKE 검색으로 시작합니다.

## 9. 레시피 하나가 사라질 때 연쇄 동작 요약

작성자가 직접 삭제하든, 탈퇴하면서 삭제를 고르든, 운영자가 삭제를 확정하든 같은 경로를 탑니다.

| 대상 | 처리 |
|---|---|
| 레시피, 레시피 옵션 | soft delete, 30일 뒤 hard delete (C-01) |
| 좋아요, 저장 | 즉시 삭제. 다른 사람의 저장 목록에서 사라짐 (R-07) |
| AI 피드백 | 보관 (품질 데이터) |
| 진행 중인 신고 | `TARGET_DELETED`로 종료 |
| 이 레시피를 가리키는 알림 | 남겨 두고, 누르면 삭제 안내 화면 (N-04) |
| 공유 URL | 삭제 안내 화면 (R-09) |

## 10. 결정 순서

스키마에 들어가는 항목부터 정해야 엔티티와 Flyway 작업을 다시 하지 않습니다.

| 순서 | 항목 | 이유 |
|---|---|---|
| 1 | C-01, C-02, U-04, U-05, U-06 | user 도메인 파일럿 전에 필요. `users.status`, 개인정보 컬럼 NULL 허용, 탈퇴 이벤트 구조가 걸려 있습니다. |
| 2 | U-01, U-02, T-01 | user·terms 엔티티의 유니크 제약과 약관 버전 구조 |
| 3 | CA-02, CA-03, CA-04, CA-05 | catalog 엔티티 구조. recipe가 이것을 참조합니다. |
| 4 | R-02, R-04, R-08, R-09, RP-03, RP-04 | recipe·report 엔티티의 컬럼과 인덱스 |
| 5 | N-02, N-05 | notification 엔티티 추가 여부 |
| 나머지 | C-03, T-02, R-03, R-11, S-02 등 | Service·Controller 단계에서 정해도 됩니다. |

디자인 팀에 요청할 화면과 문구는 따로 모았습니다.

- 탈퇴 화면: "남긴 레시피는 탈퇴 후 직접 삭제할 수 없어요" 문구 (U-05)
- 약관 재동의 화면 (T-01)
- 삭제된 레시피 안내 화면, 블라인드된 레시피 안내 화면 (R-09)
- 블라인드·삭제 통지 알림 (N-01)
- 레시피 이름 30자, 직접 입력 옵션 30자로 축소 검토 (R-02, CA-04)
- 카드 숫자가 저장 수인지 확인 (R-08)
- 알림 설정 "저장한 브랜드" 문구 변경 (N-03)
- 화면정의서의 회원 탈퇴 문구를 와이어프레임의 선택형으로 맞추기 (0-2)
